## 1. Vue d'ensemble

FemiGlow est un monorepo pnpm contenant une unique application Next.js 14 (`apps/web`). Le projet est en **Phase 1** (B2C prototype) avec un tunnel d'achat fonctionnel sur stub de paiement (COD/transfer uniquement, pas encore Stripe/CMI).

### 4.3 Pattern de gestion d'erreurs

```typescript
// Classe centralisée
class HttpError extends Error {
  code: ErrorCode;  // 20+ codes typés : unauthorized, not_found, invalid_input, etc.
  status: number;   // Auto-mappé depuis le code (400-502)
  message: string;  // Message en français
  details?: unknown;
}

// Usage dans les routes
try {
  // logique métier
} catch (err) {
  const { status, body } = formatErrorResponse(err);
  return NextResponse.json(body, { status });
}
```

Le module checkout a des erreurs spécialisées : `PriceMismatchError`, `StockInsufficientError`, `UnknownSkuError`, `IdempotencyConflictError`.

### 4.4 Idempotence

Le checkout utilise un middleware d'idempotence (`lib/checkout/api/idempotency-middleware.ts`) :

- **Pas de `Idempotency-Key`** : exécution fraîche, pas de cache
- **Clé présente, inconnue** : exécuter, persister la réponse
- **Clé présente, connue, hash correspond** : rejouer la réponse cachée
- **Clé présente, connue, hash différent** : 409 Conflict

Table `checkout_idempotency` avec TTL 24h et hash SHA-256 du body.

## 5. Authentification & sécurité

### 5.1 Auth admin (custom)

Pas de Next-Auth ni Clerk. Système custom basé sur **iron-session** :

- **Cookie** : `femiglow_admin_session`, HttpOnly, SameSite=lax, Secure (prod)
- **TTL** : 8 heures
- **Payload** : `{ adminId, email, issuedAt, expiresAt }`
- **Chiffrement** : AES-256 via `ADMIN_SESSION_PASSWORD` (≥ 32 chars)
- **Password hash** : Argon2id (memory 19456, time 2, parallelism 1)

### 5.2 Flux de login

1. Bootstrap automatique du superadmin depuis les env vars (`ADMIN_BOOTSTRAP_*`)
2. Validation Zod (`loginInputSchema`)
3. Vérification brute-force : max 5 échecs / 15 min par IP+email
4. Rate limiting : 20 requêtes / 15 min par IP
5. Vérification Argon2
6. Création session + cookie
7. Log audit (succès ou échec)

### 5.3 Middleware (`middleware.ts`)

Exécuté sur **toutes les routes** sauf `_next/static`, `_next/image`, assets statiques :

1. **Auth admin** : Pour `/admin/*` et `/api/admin/*` (sauf `/admin/login`), décode le cookie session. Redirige vers `/admin/login?next=<path>` si invalide.
2. **CSP headers** : Script-src (nonce per-request), style-src (nonce), img-src (self + CDN), connect-src (Sentry, Plausible, tracking), font-src (self), frame-src (YouTube no-cookie, Listmonk). Admin preview : `frame-ancestors 'self'`.
3. **Security headers** : HSTS preload (prod), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (ou `SAMEORIGIN` pour admin preview), `X-Robots-Tag: noindex, nofollow` sur `/admin/*`, `Cache-Control: no-store` sur `/admin/*`.
4. **Attribution Google Ads** : Capture `gclid`/`gbraid`/`wbraid` dans des cookies first-touch (90 jours).

### 5.4 Rate limiting

In-memory via `memoryStore().rateLimitCounters`. Keyed par string (ex: `login:<ip>`), limit/window configurable. Utilisé pour login et webhooks email.

### 5.5 Audit logging

Toutes les actions admin significatives sont loguées dans `audit_events` via `logAuditEvent({ action, actorId, resourceType, resourceId, meta })`.

### 5.6 Gitleaks

Pre-commit hook exécutant gitleaks avec règles custom pour `ADMIN_SESSION_PASSWORD`, `WEBHOOK_SECRET_KEY`, `CRON_SECRET`, et les chaînes de connexion PostgreSQL.

### 5.7 Anti-SSRF

Le module webhook (`lib/webhooks/anti-ssrf.ts`) valide les URLs de destination pour prévenir les attaques SSRF.

## 6. Système d'emails

### 6.1 Architecture (Outbox Pattern)

Le système repose sur un pattern **outbox** — les emails sont d'abord insérés dans `email_outbox` puis traités par un cron :

1. **Création** : `sendTransactional()` vérifie l'idempotence, la suppression, rend le template, insère dans `email_outbox` avec statut `queued`
2. **Traitement** : `/api/cron/email-outbox` pick les lignes `queued` avec `FOR UPDATE SKIP LOCKED`, tente l'envoi SMTP via Stalwart
3. **Statuts** : `queued → processing → sent | failed` (avec retry)
4. **Événements** : Chaque transition de statut insère un `email_event`

### 6.2 Templates

- **Transactionnels** : Référencés dans `catalog.ts` (`TemplateSlug`, `TemplateRegistry`), rendus via `@react-email/components` + Handlebars
- **Custom** : `email_template_custom` / `email_template_custom_version` avec versioning dans l'admin

### 6.3 Campagnes & automations

- **Audiences** : Builder d'audiences avec règles compilables, snapshots ponctuels
- **Campagnes** : Sync bidirectionnel avec Listmonk (`listmonk/client.ts`, `campaigns/listmonk-sync.ts`)
- **Automations** : Moteur d'automatisation (event/schedule triggers), runs avec états, reprise sur timeout
- **Suppression** : `email_suppression` pour bounces et désinscriptions, vérifiée avant chaque envoi

### 6.4 Webhooks entrants

- **Listmonk** : `/api/mail/webhook/listmonk` (HMAC-SHA256) → parse événements, bridge vers `user_event`
- **Stalwart** : `/api/mail/webhook/stalwart` (Bearer token) → mise à jour statuts outbox, insertion suppressions
- **Désinscription** : `/api/mail/unsubscribe` (GET/POST) avec token JWT one-click

## 7. Système de webhooks

### 7.1 Webhooks entrants (admin-configurables)

Architecture dans `lib/webhooks/engine.ts` :

- **Création** : Admin configure endpoint URL + événements souscrits + secret chiffré (AES-256-GCM)
- **Envoi** : `enqueueDelivery()` crée un enregistrement `pending` dans `webhook_deliveries`
- **Traitement** : `processBatch()` (appelé par `/api/cron/tick`) claim les livraisons pending, signe le payload HMAC-SHA256, POST à l'URL, enregistre le résultat
- **Retry** : Backoff exponentiel, statuts : `pending → in_progress → succeeded | failed | permanent`
- **Idempotence** : Clé composite `endpointId + idempotencyKey`
- **Sécurité** : Anti-SSRF, signature HMAC dans headers `x-webhook-signature` et `x-femiglow-signature`
- **Événements** : `lead.created`, `lead.step2_completed`, `lead.status_changed`, `lead.note_added`, `order.created`, `ritual.approved`, etc.

### 7.2 Webhook sortant (single destination)

- **Destination** : `OUTBOUND_WEBHOOK_URL` (env var)
- **Sources** : `from-order`, `from-chat-lead`, `from-cart-abandon`, `from-contact`, `from-wizard-step2`, `from-wizard-step1-abandon`
- **Logs** : `outbound_webhook_log` table
- **Signature** : HMAC-SHA256 dans `x-femiglow-signature`
- **Retry** : 3 tentatives avec backoff [1s, 3s, 9s]
- **Idempotence** : Vérifie existence d'un row `sent` avant envoi

### 7.3 Scanners de cron

- `cart-abandon-scanner.ts` : détecte les leads avec panier abandonné
- `lead-step1-abandon-scanner.ts` : détecte les leads ayant abandonné à l'étape 1

## 13. Frontend — Checkout & tunnel d'achat

### 13.1 Deux modes de checkout

**Mode A — Wizard embed** (`/kit` avec ancre `#commander-femiglow`) :
- `WizardShell` → étapes : `cart_review` → `lead` → `address` → `thank_you`
- État dans Zustand `wizard-store` avec localStorage persistence + migrations versionnées (v1→v2→v3)
- Étapes lazy-loadées via `React.lazy()`

**Mode B — Page dédiée** (`/commander`) :
- `CheckoutFlow` → 3 étapes : Info → Adresse → Paiement
- État dans React Hook Form + Zod (`checkoutFormSchema`)
- `FormProvider` context

### 13.2 Flux utilisateur complet

1. **Landing** (`/`) → Hero + CTA
2. **Produit** (`/kit`) → HeroProduit + `KitCommanderSectionBound` (wizard embed)
3. **Ajout panier** → `AddToCartButton` → Zustand `cart-store` → `MiniCartSlideOver` → toast "Ajouté à votre rituel"
4. **Panier** (`/panier`) → CartLayout + CartSummary
5. **Checkout** → Mode A ou B
6. **Merci** (`/merci`) → Lecture commande depuis localStorage

### 13.3 Étapes du wizard

**Étape 1 (Info)** : Prénom + téléphone marocain (+212, 9 chiffres commençant par 5-7) + consentement. Émet `lead_capture` + `generate_lead`. Crée lead via `POST /api/checkout/lead`.

**Étape 2 (Adresse)** : Autocomplete ville (DB `delivery_cities`, FR + AR) + adresse optionnelle + notes livraison. Patch via `PATCH /api/checkout/lead/[id]/address`. Émet `add_shipping_info`.

**Étape 3 (Confirmation)** : COD forcé silencieusement. Opt-in email optionnel pour récap. Crée commande via `POST /api/checkout/order`. Émet `purchase`. Vide le panier, sauvegarde dernière commande en localStorage, redirige vers `/merci?order=FG-XXXX-XXXXX`.

### 13.4 Validation

Zod schemas centralisés dans `lib/schemas/` :
- Téléphone : 9 chiffres, commence par 5-7
- Ville : min 2 caractères, pays doit être "MA"
- Paiement : enum (`cod`, `transfer`, `card`)
- Consentement : `true` obligatoire
- Email : optionnel, format validé

### 13.5 Persistence brouillon

Mode B : `checkout-draft.ts` — auto-sauvegarde chaque frappe (400ms debounce), strip les champs sensibles.

Mode A : Zustand `wizard-store` avec `persist` middleware.

### 13.6 Panier

Zustand `cart-store` avec localStorage persistence. Migration v1→v2 qui remplace `.svg` par `.png` dans les URLs d'images.

## 21. Dette technique & risques

### 21.1 Architecture

- **Pas de React Query** : Les RSC gèrent le data fetching public, mais l'admin fait des rechargements complets après chaque mutation. Pas de cache client-side, pas d'invalidation sélective.
- **Pas de Server Actions** : Tout le server logic est dans des API routes. L'admin fait des `fetch()` POST/PUT/DELETE puis rechargement de page.
- **Dual-driver DB** : Le pattern `if (drizzle) { ... } else { memoryStore }` duplique la logique pour chaque query. Le memoryStore n'est pas testé par les tests e2e.
- **Monorepo single-app** : Pas de packages partagés. Tout est dans `apps/web/src/`. Si une deuxième app arrive, il faudra extraire les libs partagées.

### 21.2 Performance

- **Pas de `loading.tsx`** : Pas de Suspense boundaries au niveau route. Les pages publiques attendent le data fetching complet avant de streamer.
- **Pas de streaming React** : Les RSC font du `async/await` mais pas de streaming incrémental.
- **Bundle chat** : LangChain + providers multi-AI est un bundle significatif. Pas de dynamic import visible pour le chat widget.
- **admin-fields.css** : 25 KB chargés conditionnellement — c'est bien, mais le CSS admin pourrait être davantage code-splitté.

### 21.3 Sécurité

- **Rate limiting en mémoire** : Le rate limiting utilise `memoryStore()` (Map en mémoire). Pas persisté. Redémarrage = reset des compteurs.
- **Pas de RBAC implémenté** : Le schéma a une table de permissions RBAC (`/admin/settings/rbac`) mais tous les admins sont superadmin. Pas de granularité de rôle.
- **CORS** : Pas de politique CORS explicite dans l'API. Les routes publiques acceptent les requêtes de n'importe quelle origine.
- **Webhook secrets** : Chiffrés en AES-256-GCM dans la DB, mais la clé est dans une env var (`WEBHOOK_SECRET_KEY`). Rotation manuelle.
- **Session cookie** : 8 heures de TTL. Pas de refresh token ni de mécanisme de révocation active.

### 21.4 i18n

- **Checkout uniquement bilingue** : Le wizard checkout a des traductions FR/AR, mais tout le reste de l'app est hardcoded en français. La Phase 2 prévoit le support RTL complet.
- **Pas de système de traduction centralisé** : Les strings sont éparpillées dans les composants.

### 21.5 Tests

- **Coverage limité** : Les seuils de coverage (80/70) sont scopés au product feed uniquement. La majorité du code n'a pas de tests unitaires.
- **Pas de tests d'intégration DB** : Le memoryStore mock n'est pas une vraie DB. Les tests e2e Playwright couvrent les flux critiques mais pas les cas limites.
- **Tests webhook** : Présents (`webhook-endpoints.test.ts`, `engine.test.ts`) mais pas de test d'intégration de bout en bout.

### 21.6 Email

- **Listmonk en iframe** : L'admin email utilise un proxy same-origin vers Listmonk qui est cassé à cause des chemins absolus HTML de Listmonk (`/admin/static/...`). Solution actuelle : sous-domaine dédié `listmonk.femiglow-maroc.com` avec login séparé (pas SSO).
- **Pas de file d'attente persistante** : L'outbox email est en DB, mais le picking se fait par cron (1 min d'intervalle). Pas de file de messages (RabbitMQ, SQS, etc.).

### 21.7 Paiement

- **COD uniquement** : Le checkout force silencieusement le paiement COD. Stripe est prévu en Phase 2. Le webhook Stripe existe déjà mais n'est pas activé.
- **Pas de vérification de stock atomique côté client** : La réservation de stock est atomique côté serveur (CAS sur `product_stock`), mais le client ne voit pas les mises à jour en temps réel.

### 21.8 Chat

- **Kill switch uniquement** : `CHAT_ENABLED` est un booléen global. Pas de feature flag granulaire.
- **Budget mensuel** : Pas de mécanisme de hard stop côté code — le budget est monitoring only.

### 21.9 Data

- **90+ tables** : Le schéma est très étendu pour une Phase 1. Beaucoup de tables sont probablement vides ou peu peuplées (experiments, email_automation, etc.).
- **Pas de soft-delete générique** : Certains modèles ont un soft-delete (`archived_at`, `deleted_at`), d'autres non. Pas de convention uniforme.

## 22. Recommandations

### Priorité haute

1. **Ajouter `loading.tsx`** pour les routes publiques avec Suspense boundaries. Cela permettrait le streaming incrémental et améliorerait le FCP/LCP.
2. **Implémenter RBAC** : Le module existe dans l'admin (`/admin/settings/rbac`) mais n'est pas câblé. Ajouter des rôles (viewer, editor, admin) avec permissions granulaires.
3. **Rate limiting persisté** : Migrer vers Redis ou la DB pour le rate limiting. Le memoryStore est perdu au redémarrage.
4. **CORS policy** : Définir une politique CORS explicite pour les API publiques.
5. **Coverage tests** : Étendre les seuils de coverage au-delà du product feed. Viser 60% global minimum.

### Priorité moyenne

6. **React Query pour l'admin** : Remplacer les rechargements de page par du data fetching client-side avec cache et invalidation sélective.
7. **Extraire les libs partagées** : Créer un package `@femiglow/shared` pour les schemas Zod, les types, et les utilitaires communs (préparation pour une éventuelle 2ème app).
8. **i18n centralisé** : Extraire les strings hardcodées dans des fichiers de traduction. Utiliser next-intl ou un système custom pour préparer la Phase 2 RTL.
9. **Chat dynamic import** : Lazy-loader le chat widget pour réduire le bundle initial.
10. **Soft-delete uniforme** : Adopter une convention de soft-delete cohérente (tous les modèles supprimables avec `deleted_at`).

### Priorité basse

11. **Streaming React** : Utiliser `renderToReadableStream` pour les RSC avec Suspense boundaries, permettant d'envoyer du HTML progressif au client.
12. **File de messages pour les emails** : Remplacer le polling cron par une file de messages (Redis + BullMQ ou similaire) pour l'outbox email.
13. **Rotation automatique des secrets webhook** : Implémenter une rotation périodique des clés de chiffrement AES-256-GCM.
14. **Session refresh** : Ajouter un mécanisme de refresh token ou de session glissante pour l'admin.
15. **Monitoring** : Le DSN Sentry est configuré mais pas de vérification active du taux d'erreurs. Mettre en place des alertes.
